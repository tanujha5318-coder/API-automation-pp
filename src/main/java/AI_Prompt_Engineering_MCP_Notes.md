# AI Prompt Engineering & MCP — Learning Notes

**Today's learning task | QA / SDET perspective**

## 1. Tokens

A **token** is a unit of text processed by a language model. It may be a whole word, part of a word, punctuation, or another text unit. Tokens are not the same as words or characters.

The lesson gives rough English heuristics:
- 1 token ≈ 4 characters.
- 1 token ≈ ¾ of a word.

These are estimates only. Actual tokenization depends on the model's tokenizer, language, and text.

### Example from the screenshot

Prompt: `Write test cases for login page.`

The slide's approximate breakdown is:
- `Write` → 1 token
- `test` → 1 token
- `cases` → 1 token
- `for` → 1 token
- `login` → 1 token
- `page` → 1 token
- `.` → 1 token

**Slide total: 7 tokens**, with a note that internal encoding adjustments may make it approximately 8. The exact count can differ by tokenizer.

## 2. Input tokens and output tokens

Tokens are counted in two directions:

- **Input tokens:** prompt and context supplied to the model.
- **Output tokens:** text generated by the model.

Simple formula:

`Total tokens per request = input tokens + output tokens`

Conversation history, retrieved documents, tool results, and structured instructions can also contribute to input usage, depending on the application.

## 3. Why token saving matters

The lesson highlights **cost efficiency**:
- Some paid LLM APIs charge based on token usage.
- Vague prompts can lead to multiple clarification exchanges.
- Clear prompts can reduce repeated context and unnecessary tokens.

The slide's example compares:
- 450 tokens — vague prompt with back-and-forth
- 305 tokens — refined in one shot
- 145 tokens — illustrative saving

These are lesson-example figures, not universal pricing or performance guarantees. Actual pricing varies by provider and model.

## 4. Context window limit

A **context window** is the amount of tokenized information a model can process as context for a request. It is model- and product-specific.

The screenshot uses GPT-4 Turbo with 128K tokens as an example. Do not treat that number as a current limit for every model.

If the available context is exceeded, an application may truncate, summarize, retrieve selectively, or otherwise manage earlier information. It is not safe to assume every model simply drops the oldest messages in the same way.

## 5. Best practices to save tokens

1. **Be precise from the start** — avoid vague, open-ended prompts.
2. **Remove unnecessary filler words** — keep all meaningful requirements.
3. **Summarize important information** — avoid pasting the same full document repeatedly.
4. **Use role + context + constraints** — put the task in one compact, structured prompt.
5. **Chunk large tasks** — split independent work into smaller requests; keep dependent steps together.

## 6. AI, LLM, and AI agents

### Artificial Intelligence (AI)
AI is the broad field of building systems that perform tasks such as understanding language, recognizing patterns, planning, and generating content.

### Large Language Model (LLM)
An LLM is an AI model trained to process and generate language. It uses the context provided at runtime to produce a response.

### AI Agent
An AI agent is an application that uses a model to interpret a goal, plan or select steps, use tools, observe results, and continue toward the goal.

A useful simplified view is:

`AI Agent ≈ LLM + instructions + orchestration/decision loop + tools + context + permissions`

The screenshot says **“AI Agent = LLM + MCP Servers.”** This is a useful teaching shortcut, but not a complete technical definition. MCP is an integration protocol; it does not alone make a model autonomous or guarantee correct and safe behavior.

## 7. What is MCP?

**MCP = Model Context Protocol.**

MCP is an open protocol that standardizes how AI applications connect to external context sources and tools.

The screenshot compares MCP to **USB-C**:
- USB-C gives devices a common connection interface.
- MCP gives AI applications a common way to connect to compatible tools and data sources.

### Why MCP is useful
- Standardizes communication between AI applications and external systems.
- Allows a host application to connect to multiple specialized servers.
- Makes integrations reusable across compatible AI applications.
- Can connect to local data sources and remote services/APIs.
- Supports controlled access to tools and context.

## 8. MCP architecture: Host, Client, Server

### Host
The AI application the user interacts with. It coordinates the model and manages MCP connections.

### Client
The protocol component inside the host. It maintains a connection to a particular MCP server and exchanges MCP messages. A host can use multiple clients to connect to multiple servers.

### Server
A program that exposes specific capabilities or context through MCP. It may access local files, a database, or a remote API, according to its configuration and permissions.

### Typical flow

1. User gives a task to the AI host.
2. The model/host determines which context or tool is needed.
3. The MCP client sends a request to the relevant server.
4. The server accesses its permitted system and returns a result.
5. The host supplies the result to the model.
6. The model responds or chooses the next step.

## 9. MCP capabilities

MCP servers can expose three core capability types:

- **Tools:** Executable operations, such as approved browser actions, database queries, or API calls. Tools can change external state, so permissions and confirmations matter.
- **Resources:** Contextual data, such as files, database schemas, or documentation. These are commonly read-oriented.
- **Prompts:** Reusable prompt templates that standardize recurring workflows, such as a code review checklist.

## 10. MCP examples from the screenshots

| MCP example | What it can connect to | QA / SDET use case |
|---|---|---|
| Playwright MCP | Browser automation | Inspect a permitted test UI, run browser interactions, investigate UI failures |
| MySQL MCP | Database | Check test data, verify persisted records, compare UI/API results with DB state |
| REST API MCP | APIs / external services | Call approved test endpoints, inspect responses, validate API workflows |
| Filesystem MCP | Local files and folders | Read test data/logs and create report artifacts in an allowed project directory |
| Excel MCP | Spreadsheet files | Read test scenarios, update execution sheets, analyze test results |

These are illustrative integration categories. The exact actions depend on the MCP server implementation and configured access.

## 11. Practical QA / SDET example

**Goal:** Investigate why a login regression test is failing.

1. Ask the AI host to investigate the failure and provide the test environment, test case ID, and expected behavior.
2. Use a Playwright-capable MCP server to inspect the permitted login page.
3. If authorized, use an API MCP server to retrieve the login response and status details.
4. Use a read-only database MCP server to verify the expected test-user state.
5. Use a filesystem MCP server to read the relevant test log or report.
6. Correlate the evidence and draft a reproducible defect report. The QA engineer verifies the evidence before changing code or test data.

This is an example workflow, not a claim that every server supports these exact actions.

### Security reminders
- Use test environments and test accounts.
- Never paste passwords, access tokens, or secrets into prompts or GitHub.
- Prefer read-only database access for investigation.
- Restrict filesystem access to the required project folder.
- Review tool actions before allowing changes to external systems.
- Verify AI-generated conclusions against actual test evidence.

## 12. Copy-ready QA prompt template

```text
Role: Act as a Senior QA Automation Engineer.

Context:
I am testing [application/module] in [test environment].
Feature: [feature name]
Requirement / acceptance criteria: [paste concise requirements]
Available evidence: [test case, API response, logs, screenshots, database schema]

Task:
[State one specific task, e.g. analyze the login failure or generate regression test cases.]

Constraints:
- Do not assume missing requirements.
- Separate confirmed facts from assumptions.
- Do not use production data or perform destructive actions.
- Mask credentials, tokens, and personal data.
- Include positive, negative, boundary, and error scenarios where relevant.

Output:
1. Summary
2. Preconditions and test data
3. Test scenarios / steps
4. Expected results
5. Risks and open questions
6. Evidence needed to verify the result
```

## 13. Key takeaways

- Tokens are the units a model processes; words and tokens are not identical.
- Input and output both contribute to token usage.
- Context windows are model-specific capacity limits, not unlimited memory.
- Precise prompts reduce ambiguity and repeated clarification.
- MCP standardizes connections between AI hosts and external tools/data.
- Remember: **Host = AI application, Client = connection component, Server = capability provider.**
- MCP can support QA workflows involving browser automation, APIs, databases, files, and spreadsheets—but access must be controlled and results must be verified.
